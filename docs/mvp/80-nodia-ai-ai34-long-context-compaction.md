## Alcance y diseño

Continuidad canónica entre turnos y cambios de conexión/modo/modelo. Se elimina el corte de carga de 128 mensajes y se usa una ventana SQL limitada por bytes. Los mensajes originales son inmutables y permanecen en Nodia; compactar modifica sólo la representación enviada al modelo. No se implementan embeddings, búsqueda semántica, sesiones nativas opacas, memoria compartida ni nuevas herramientas de escritura.

Antes de inferir, el worker incorpora conocimiento publicado, preferencias aceptadas vigentes, memoria validada, mensajes posteriores y referencias operativas actuales. Si el historial supera la mitad del presupuesto de contexto, la ventana está incompleta o el prompt completo no cabe, la fase context puede realizar una compactación. Usa exactamente la selección actual y no expone herramientas ni adjuntos a esa llamada. Una compactación máxima por run comparte el presupuesto de tres dispatches; no hay bucle de compactaciones ni reintento de respuestas inciertas.

La ventana de historial ocupa como máximo tres cuartos de los 256 KiB propios de Nodia. Puede procesar un prefijo de un chat legacy mayor; excluye siempre el mensaje actual del dueño. Tras guardar el resumen, inference vuelve a cargar contexto y comprueba el presupuesto. Si todavía no cabe, termina con un límite explícito sin borrar originales ni cambiar la selección.

## Contrato del resumen

Objeto cerrado `schema_version:1`, con cinco arrays `facts`, `decisions`, `questions`, `entities`, `requirements`. Cada elemento contiene únicamente `text` y `source_seqs`, secuencias positivas ordenadas y únicas. Límite 128 por colección y 32 KiB de respuesta/resumen. Cada texto debe aparecer literalmente en cada fuente citada o en una entrada ya validada del snapshot previo. No se aceptan paráfrasis, citas inventadas, referencias futuras, campos adicionales ni JSON parcialmente recuperado. Cada mensaje nuevo visible con texto no vacío debe quedar representado por al menos una cita; no puede desaparecer un mensaje entero. Esta cobertura no prueba que la cita conserve cada detalle semántico. El contenido del resumen va serializado dentro del campo text del envelope answer del transporte, evitando instrucciones contradictorias sobre el JSON externo. El resumen debe reducir bytes respecto al historial y memoria anteriores.

La continuidad del resumen anterior es monotónica por categoría, cita y secuencias: no puede desaparecer una entrada validada para ganar espacio. Eso limita la duración máxima de una conversación; ante agotamiento se pide acotar o abrir otra conversación. No se afirma recordar exhaustivamente todos los detalles: el modelo selecciona las citas y la validación demuestra su procedencia literal, no la exhaustividad semántica. Las contradicciones y preguntas permanecen datos históricos, no órdenes ni hechos de negocio confirmados.

## Persistencia mínima

M4 añade `nodia_ai_context_snapshots`: nueve columnas (`id`, `conversation_id`, `revision`, `through_message_seq`, `source_hash`, `summary`, `scope_manifest`, `builder_contract_version`, `created_at`). Índices de revisión y secuencia; FK del chat con CASCADE. Run añade `context_snapshot_id` nullable y FK compuesta con su chat, impidiendo referencias cruzadas. No tabla de intentos de compactación ni copia de cada mensaje.

El hash SHA256 se calcula en PostgreSQL sobre la proyección canónica completa del prefijo: identidad, secuencia, rol, autor, estado, scope y partes ordenadas. No requiere extensión pgcrypto ni descargar el prefijo completo en Node. La consulta recorre el prefijo completo en cada revalidación; acota transferencia/memoria de Node, pero no convierte ese trabajo PostgreSQL en O(1). La revisión se asigna bajo bloqueo del chat. Los snapshots se insertan, no se editan. Su versión de constructor, scope exacto y hash deben coincidir antes de reutilizarlos. Un snapshot inválido se descarta como contexto y se reconstruye desde fuentes visibles.

El almacenamiento de snapshots cuenta en las cuotas de chat/dueño. Antes del dispatch se reserva espacio bajo el mismo bloqueo global de admisión; un run unknown conserva la reserva. Al guardar, se sustituye la reserva por los bytes JSONB reales y se preserva espacio para la respuesta. La purga del chat elimina snapshots y referencias junto con mensajes/adjuntos; preferencias aceptadas sobreviven conforme AI-33. El rollback de migración rechaza datos de snapshots o referencias poblados.

## Autoridad, operaciones y concurrencia

Se filtran fuentes no autorizadas antes de entregar texto a Node. Tras observar disponibilidad y dentro del armado durable se revalidan permisos actuales/intersección del scope admitido, huella del historial, preferencias y referencias operativas. Se vuelve a comprobar al recibir el resumen y antes de persistirlo. Un cambio invalida el intento, conservando originales y contexto previo; una respuesta nativa terminal permite cerrar como fallo conocido y liberar el perfil sin repetirla.

La delegación comprueba además opt-in/revisión de routing dentro del callback de armado, bajo el lock del chat. Si se desactiva entre preparar la solicitud y reservar el perfil, devuelve routing_disabled antes del envío. La regresión reproduce esa carrera y verifica cero llamadas al adaptador; el runtime conserva un fallo conocido y libera el slot, sin inventar un resultado incierto ni depender de un recibo nativo inexistente.

`recovery_refs` se obtiene mediante los cargadores nativos de propuestas/ejecuciones y autoridad vigente. Incluye todas las referencias pendientes hasta 128; superar el límite produce error explícito. Incluye además las 25 referencias históricas más recientes con total/incluidos/más, sin copiar comandos, secretos o confirmaciones. Si hay más historia, el modelo debe consultar estados anteriores mediante herramientas autorizadas antes de afirmar un resultado. Cargar referencias nunca aplica ni reanuda efectos.

## Presupuesto del adaptador

El límite propio de 256 KiB corresponde al contenido nativo inicial controlado: prompt completo, instrucciones del protocolo, catálogo MCP, serialización, referencias a adjuntos y definición propia del agente CLI. Esa definición determinista (incluido su frontmatter) se suma en overhead y total; no se ignora como si fuera contexto privado del SDK. Un endpoint privado autenticado mide los mismos constructores usados para ejecutar, sin abrir sesiones, archivos ni SDK. Devuelve contrato `nodia-ai-context-budget/1`, ámbito `initial_native_prompt`, bytes canónicos/catálogo/overhead/total, techo y `model_context_tokens:null`. El campo separado `first_mcp_listing_upper_bound_utf8_bytes` reserva una cota explícita del primer tools/list, porque repite el catálogo que ya estaba en el prompt. El preflight suma esa reserva a la medida inicial para decidir si compactar, sin presentar contenido futuro como ya enviado. No convierte bytes en tokens ni inventa la ventana del proveedor.

Sin archivos nativos Agentic la medida es exacta; con ellos es una cota superior explícita derivada del contrato de rutas privadas. La frontera real comprueba siempre el prompt exacto antes de abrir el proceso del proveedor. El presupuesto del catálogo (74 herramientas/128 KiB) continúa siendo un límite independiente de transporte, no una franquicia adicional sobre los 256 KiB. Durante MCP, el puente lleva el presupuesto acumulado del prompt inicial exacto más cada respuesta JSON-RPC completa que entrega al CLI: discovery, resultados, rechazos y replays. Cuenta serialización y la duplicación entre texto y structuredContent; no trunca una respuesta para hacerla caber. Una reclamación persistente por intento impide reiniciar el contador al relanzar el puente, y un marcador de exceso impide aceptar un éxito del CLI que ignore la caída de MCP. No se repiten ni deshacen callbacks ya confirmados.

Este control mide contenido observable bajo control de Nodia. El contexto interno, razonamiento, instrucciones privadas y transformaciones multimodales que agregue el SDK/proveedor no son observables; no se declara una ventana total real del modelo. Los originales binarios conservan sus límites y verificaciones por formato independientes; no se convierten sus bytes en tokens.

## Errores y experiencia

`context_limit`, `compaction_invalid`, `context_snapshot_invalid` y `context_sources_changed` se muestran en ES/EN con acciones comprensibles: acotar, revisar o iniciar una petición nueva. Se conserva historial y borrador actual. No se promete que no hubo dispatch: el fallo puede aparecer después de una compactación terminada. No hay reenvío automático ni confirmación implícita. Web sigue conversacional; cambiar a Agentic continúa sujeto al consentimiento y comprobaciones existentes.

## Verificación y pendientes

Casos de uso, SQL compilado desechable, presupuesto nativo Python/Node y UI verificados; aceptación Gemini real parcial. La ficha permanece draft/unregistered y ADR propuesto; no nueva publicación MCP ni aceptación productiva implícita.

## Investigación instrumentada de Agentic

El [quinto request generativo](../evidence/nodia-ai-ai34-live-agentic-instrumented-attempt01.json), extracción Agentic independiente con nonce nuevo y sin replay, terminó a 111.261 ms. El [diagnóstico estructural](../evidence/nodia-ai-ai34-agentic-instrumented-diagnostic.json) sitúa 2.837 ms en preflight y 108.415 ms en CLI. El CLI emitió SUCCESS e intentó run_command y view_file; el gate negó esas herramientas y el validador rechazó attachment_cli_unexpected_tool. Ese intento no fue un timeout y no demuestra fallo del proveedor. Quedó conciliado como abandoned_unknown con proceso cerrado y ACK; no se aceptó una respuesta que violara permisos.

La instrumentación propia se verificó con 415 pruebas Linux y 413 correctas/dos omisiones históricas Windows; [activación diagnóstica](../evidence/nodia-ai-ai34-native-diagnostics-activation.json) de 98 fuentes, sin cambios de selección, timeout, esquema, build Node ni permisos. El texto usaba el agente predeterminado del CLI, más amplio que esta tarea. Se investigó restringir su definición nativa a finish para texto, y catálogo MCP más finish cuando corresponda, conservando el gate como segunda frontera. La definición del agente bajo control de Nodia debe contar en overhead/total y en el acumulado MCP: no es contexto privado desconocido del SDK. La corrección se verificó con otra imagen, pruebas y canario identificados por separado.

La corrección se implementó después con roles propios mínimos, identidad exacta en init y definición contabilizada. [Offline del rol](../evidence/nodia-ai-ai34-native-role-offline.json): 419/419 Linux y Windows 417 correctas/dos omisiones históricas; [presupuesto final](../evidence/nodia-ai-ai34-adapter-budgets.json): 35 comprobaciones. [Activación incremental](../evidence/nodia-ai-ai34-native-role-activation.json): Node931, imagen de 99 fuentes, respaldo anterior completo y cambios sólo en ProcessStage y dos assets de conocimiento. No migraciones nuevas ni cambios de configuración. Repetición SQL aislada de 36 checks correcta; chat R05, entorno, mounts y nginx intactos, cero pendientes. El [linaje del conocimiento](../evidence/nodia-ai-ai34-knowledge-lineage.json) conserva 27 fragmentos/67 contratos idénticos; cambia el hash de una fuente documental, con pin propio por canario. Los resultados de ese ensayo se detallan a continuación.

El [canario de roles](../evidence/nodia-ai-ai34-live-agentic-role-attempt01.json) verificó compactación Agentic en 86,6 segundos y continuidad en 35,2, con dos recibos terminales ACK. Preservó cinco categorías citadas: 151.720 bytes canónicos→656 de resumen; la respuesta posterior usó sólo memoria y cola actual. La tercera solicitud MCP terminó ERROR/exit3 en 3,7 segundos, cuatro eventos y cero callbacks; [diagnóstico](../evidence/nodia-ai-ai34-role-mcp-diagnostic.json) confirma presupuesto sobrado, pero no conserva una causa textual. Ese resultado no demuestra fallo del proveedor ni que call_mcp_tool sea un nombre válido en el frontmatter del agente. Se retira únicamente el rol MCP experimental y se conserva el transporte/gate anterior; texto y reader propios permanecen verificados. Se añaden categorías cerradas de error/stderr, sin conservar mensajes crudos, para la siguiente prueba explícita. Ocho solicitudes generativas hasta este ensayo: cuatro respuestas de texto aceptadas y cuatro fallos cerrados/ACK, sin efectos de negocio ni replay.
