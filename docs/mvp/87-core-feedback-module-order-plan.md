## Hallazgos comprobados antes de implementar FX-01

### Avisos de permisos y sesión

- [authorizationService](../../nodia-client/src/services/authorizationService.ts) emite `sileo.success(auth:context_loaded)` después de **cada GET exitoso** de `/authorization/context`. No compara permisos ni distingue una acción humana de una revalidación. El texto actual afirma un cambio que el GET no acredita.
- El hook tiene `staleTime` de cinco minutos y deshabilita refetch al montar, foco y reconexión; **no tiene `refetchInterval`**. StaleTime no significa polling periódico.
- [useSessionLifecycle](../../nodia-client/src/providers/hooks/useSessionLifecycle.ts) programa la renovación treinta segundos antes del vencimiento. [authSession](../../nodia-client/src/config/authSession.ts) activa/desactiva `isRefreshing`; [hasActiveSession](../../nodia-client/src/store/authStore.tsx) exige que no esté renovándose. Así, el `enabled` de la consulta de contexto puede pasar de true a false y de nuevo a true.
- Una consulta stale puede volver a ejecutarse en esa reactivación aunque `refetchOnMount` sea false. Reproducción ejecutada con QueryObserver de la dependencia instalada, sin red ni archivos: caché sintética de seis minutos, staleTime cinco, mismos flags; montaje → cero lecturas, enabled false→true → una lectura con contexto idéntico. Esto demuestra el mecanismo; no mide la periodicidad del episodio concreto del usuario.
- El GET también se revalida tras determinadas mutaciones de usuarios, roles, acciones, módulos/grupos y recibos Core de NodiaAI; no todas las mutaciones tienen la misma invalidación. Esas invalidaciones mantienen la autorización actual y deben conservarse. Referencias: [mutaciones de módulos](../../nodia-client/src/modules/generalSettings/pages/Modules/infrastructure/useServices.ts), [ejecuciones NodiaAI](../../nodia-client/src/modules/nodiaAi/infrastructure/useExecution.ts).
- `authSession` también emite «Sesión validada» (`auth:session_restored`) y «Sesión renovada» en procesos automáticos. El [QueryCache global](../../nodia-client/src/config/reactQuery.ts) y el hook de contexto pueden notificar ambos el mismo error: el timestamp local no coordina con el responsable global.

### Módulos y navegación

- Las entidades [Module](../../nodia-server/src/module/entities/module.entity.ts) y [ModuleGroup](../../nodia-server/src/module-group/entities/module-group.entity.ts) y sus DTOs no tienen campo de orden persistido.
- [ModuleService](../../nodia-server/src/module/module.service.ts) y [ModuleGroupService](../../nodia-server/src/module-group/module-group.service.ts) no fijan un orden predeterminado estable en la lectura HTTP común; el desempate por ID sólo se añade en la variante con EntityManager. No se puede prometer conservar un orden SQL que hoy no está definido.
- `GET /modules?includes=true` ya incluye el grupo y agrega traducciones por conjuntos. La página [Modules](../../nodia-client/src/modules/generalSettings/pages/Modules/Modules.tsx) ya lo consume; no hace falta un endpoint nuevo ni una consulta por grupo para dibujar cabeceras.
- El [contexto de autorización](../../nodia-server/src/authorization/authorization.service.ts) agrupa módulos pero no ordena sus arrays. [Sidenav](../../nodia-client/src/layouts/components/Sidenav/Sidenav.tsx) aplica reverse y prioridades por texto de la clave: negocios primero, ajustes/admin al final. Esa heurística debe retirarse para que mande la BD.
- El [contrato actual](../../nodia-client/src/modules/generalSettings/pages/Modules/CONTRACT.md) pagina registros de módulos; los grupos administrativos tienen su paginado independiente. Las tarjetas móviles y tablas desde sm comparten filtros, acciones y estado.

## Política de notificaciones — FX-01

| Situación | Feedback previsto |
|---|---|
| Carga inicial de contexto, rehidratación, renovación de sesión o revalidación automática | Sin toast de éxito; actualizar datos y controles normalmente. |
| Guardar usuario, rol, módulo, grupo o asignación desde una acción explícita | Un único toast específico de la mutación; la posterior lectura del contexto no añade «Permisos actualizados». |
| Login/logout solicitado por la persona | Conservar su feedback específico. |
| Reintento explícito de sesión después de un error | Conservar estados de carga/error y recuperación de la vista; «Sesión validada» sólo tras completar el botón Reintentar, desde su handler humano, sin éxito genérico en el transporte compartido. |
| Pérdida efectiva de acceso a la tarea/ruta actual | Conservar bloqueo/redirección. Verificar el feedback del guard y añadir un aviso específico sólo si hace falta explicar la interrupción; no atribuir al guard un toast que hoy no emite. |
| Error al obtener el contexto | Un solo toast por fallo compartido, más estado local y reintento; no suprimir el error. |

Implementación mínima: retirar el éxito de `getAuthorizationContext` y los éxitos técnicos automáticos de renovación/restauración, manteniendo el flujo de sesión y errores. Esto aplica la petición del usuario de no anunciar trabajo background; el POST técnico de renovación no se presenta como una mutación funcional humana. Elegir un único responsable del error de contexto, usando el mecanismo local/global existente y deduplicación por error/consulta compartidos, también con varios consumidores.

No cambiar staleTime, temporizadores, JWT, revalidaciones ni `hasActiveSession` para ocultar el síntoma. No añadir polling, fingerprints, endpoints de versiones o un sistema de eventos. Avisar sobre cambios externos de permisos que no afectan la tarea actual queda fuera de este fix; si se incorpora después, debe comparar autoridad efectiva y excluir iconos, traducciones y orden.

## Contrato propuesto de orden — FX-02

Refinamiento solicitado el 2026-10-25, inicialmente sólo planificación y posteriormente autorizado para FX-02: la tabla representa el orden de presentación; las altas van al final y el usuario mueve filas mediante controles. Sustituye la propuesta inicial de editar números manualmente y permitir empates. Decisión técnica [ADR-078 propuesto](../architecture/decisions/ADR-078-module-order-and-atomic-moves.md); no marca aprobado el documento; el corte de implementación FX-02 se registra al final.

1. **Dos ámbitos de orden:** `module_groups.sort_order` ordena grupos globalmente; `modules.sort_order` ordena módulos sólo dentro de su `module_group_id`. Entero PostgreSQL no negativo, NOT NULL. Menor valor aparece antes; «lo más bajo» se interpreta como **última fila**, no menor número. Mantener IDs bigint como strings.
2. **Alta al final:** sólo para registros realmente nuevos, asignar en Server `COALESCE(MAX(sort_order), -1)+1` del ámbito completo, incluidos inactivos; primer registro 0. Grupo nuevo al final del catálogo; módulo nuevo al final de su grupo. No aceptar un `sort_order` arbitrario en los DTOs CRUD ni mostrar un campo numérico obligatorio. Editar, reactivar o recuperar un registro existente por key conserva su posición; cambiar un módulo de grupo lo coloca al final del destino. Borrar deja huecos; no renumerar hermanos en cada operación. Si se agota el rango entero, rechazar sin escribir y tratar la normalización como mantenimiento explícito.
3. **Integridad y concurrencia:** reutilizar [runCoreAuthorityTransaction](../../nodia-server/src/authorization/core-authority-transaction.ts), que ya serializa escritores Core antes de leer; no crear tabla de coordinación, locks globales adicionales o secuencias por grupo. Validar no negatividad y unicidad por ámbito en BD: `UNIQUE(sort_order)` de grupos y `UNIQUE(module_group_id, sort_order)` de módulos, diferibles para un swap transaccional. Dos altas simultáneas deben terminar con posiciones distintas; las constraints también protegen escrituras fuera del camino feliz.
4. **Movimientos atómicos:** contratos administrativos `PATCH /module/:id/order` y `PATCH /module-group/:id/order`, implementados sin registrarlos como herramientas. `direction:up|down` compara posición y vecino inmediato esperados e intercambia dos posiciones. La ampliación solicitada de arrastre añade `direction:before|after`: `expected_neighbor` identifica el destino por ID/rango, obligatorio y distinto del origen, y Server rota sólo el intervalo afectado dentro de una transacción Core, conservando sus rangos y huecos. Cada petición incluye posición actual esperada; para módulos, también grupo esperado, compartido por origen/destino. No mover un módulo fuera de su grupo. Extremo sin vecino o colocación ya coincidente es no-op explícito, nunca wrap. No encadenar PATCH vecinos, ejecutar dos PUT ni enviar todo el catálogo desde Client. Su adopción se distingue en el corte final.
5. **Estado obsoleto y red:** si cambió identidad, grupo, posición o vecino, responder409 sin efectos y refrescar la vista con mensaje específico. Deshabilitar controles durante una petición y sin reintento automático de movimientos. Si hay timeout/resultado incierto, releer y conciliar antes de habilitar un nuevo intento humano; no anunciar fallo definitivo o repetir el swap ciegamente. La precondición evita una repetición inmediata sobre una posición ya cambiada; no se promete idempotencia permanente ni detección ABA sólo con posiciones/timestamps. Si se exige esa garantía adicional, especificar versión monotónica antes de implementarla.
6. **Lectura y orden canónico:** grupos `(sort_order ASC, id ASC)`; módulos `(grupo.sort_order ASC, grupo.id ASC, módulo.sort_order ASC, módulo.id ASC)`, **antes** de skip/take y propiedad del servidor. `GET /modules` y `/module-groups` mantienen filtros/meta actuales. El modo Ordenar solicita metadata administrativa de vecinos/extremos junto a la página, calculada por conjuntos sobre el ámbito completo antes de paginar; no una consulta por fila. Retornar grupo y vecinos de grupo necesarios para sus cabeceras en ese mismo presupuesto acotado. Ransack admite un campo `q[s]`, no una tupla SQL; no ampliar su gramática. Orden explícito de otros consumidores conserva su contrato; las vistas agrupada/Ordenar no ofrecen un sort de columnas que contradiga el canónico.
7. **Presentación y caché:** ordenar los arrays del contexto autenticado en Server y consumirlos en Sidenav/Home sin heurísticas por nombre ni reverse. Tabla y navegación comparten el criterio; navegación filtra lo no autorizado/inactivo conservando el orden relativo. Conservar traducciones por lote y relación necesaria para ordenar aunque `includes=false`, sin alias duplicados o filas multiplicadas. Invalidar contexto Redis y consultas afectadas después del commit, incluyendo módulos al mover un grupo; no emitir éxitos genéricos de permisos, conforme a FX-01.
8. **Migración y entrega:** inventariar grupos, definir y registrar el orden inicial, hacer backfill determinista con valores distintos por ámbito y después añadir constraints. La prioridad histórica negocios/ajustes orienta ese orden inicial, sin prometer identidad de un orden SQL antes indefinido ni fijar IDs privados en código. No añadir DEFAULT0 a todas las altas porque colisionaría. Ensayar migración, rollback y escritores/seed/upserts existentes; planificar drenaje de escritores antiguos antes del corte para no mezclarlos con columnas administradas por Server. Cache antiguo debe invalidarse o vencer de forma comprobada. Sin migrar ni desplegar durante esta definición.

## Tabla agrupada — FX-03

- Reutilizar la consulta paginada con grupo y renderizar una cabecera por grupo que aparezca en esa página. Cada cabecera identifica el grupo; cada fila conserva acciones del módulo y su asa de orden. Los grupos se mueven desde su panel global, incluidos los vacíos, que no fabrican módulos en esta tabla. El arrastre no se ofrece desde cabeceras repetidas.
- **Paginación por módulos**, no por grupos. Un grupo puede continuar en otra página y repetir cabecera. Contadores de cabecera, si se muestran, describen sólo los registros visibles; `meta.total_items` sigue siendo cantidad de módulos filtrados. No afirmar total de hijos sin agregado backend.
- No usar `all=true` para sustituir el paginado del listado ni añadir una consulta por grupo. El catálogo auxiliar existente para filtros no se transforma en la fuente de la tabla.
- **Botón «Ordenar» / «Terminar»:** el modo normal conserva Activo por defecto, búsqueda y filtros. Entrar a Ordenar es una acción explícita que muestra Todos (activos/inactivos), sin búsquedas, filtros parciales ni sort alternativo; guarda el estado normal y lo restaura al salir. Así no se intercambia con una fila oculta por un filtro. Mantener paginado acotado, con aviso de que el orden abarca todas las páginas. No convertir el selector normal de actividad en switch ni alterar su contrato.
- **Asa antes de ID:** por petición posterior del usuario, el modo Ordenar muestra un asa en cada módulo y en las filas del panel global de grupos; las tarjetas xs muestran el asa antes de su contenido. Drag Pointer ratón/touch sólo respecto de filas visibles del mismo tipo/ámbito, con indicador antes/después; un drop equivale a una petición atómica. Teclado con asa enfocada: ↑/↓ mueve respecto del vecino global y Escape cancela; no requiere arrastrar para operar. Target44px y textos ES/EN; sin números manuales. Los botones de entrada/salida del modo siguen contained y una ayuda visible explica cómo mostrar las asas.
- **Resultado persistido:** guardar cada movimiento al completar su petición; no hay un botón de Guardar que envíe arrays completos después. Mostrar éxito específico una vez, invalidar lecturas después del commit y conservar información durante refetch. «Terminar» sólo sale del modo, no descarta movimientos confirmados. No anunciar reordenamiento al entrar/salir sin modificar datos. Se retiran Copiar ID de tablas/tarjetas, conservando ID visible y Copiar URL.
- **Límites de página:** vecinos/extremos del teclado provienen de metadata del servidor, nunca de asumir que la primera/última fila cargada es el extremo del grupo. Un paso puede cruzar página; el drag sólo usa filas cargadas. Reubicar la consulta para mantener visible la fila movida según la posición/página autorizada del Server. Si una modificación concurrente impide ubicarla, mostrar aviso y releer sin cambiar a otra entidad silenciosamente. No consultar todas las páginas para encontrarla.
- **Cambios de contexto:** si se pierde permiso, sale el grupo/registro o aparece un conflicto, bloquear el movimiento y recuperar la vista; no perder formularios abiertos ni cambiar el padre mediante flechas. Los filtros siguen pudiendo usarse en modo normal, pero no presentan un universo parcial como orden completo.
- Desde sm: tabla con cabeceras de grupo y scroll horizontal local. En xs: las tarjetas actuales bajo las mismas cabeceras. Misma consulta, estado y acciones; no montar ambas variantes activas ni perder borradores/foco al redimensionar. Conservar controles y expansión con semántica accesible.
- Mostrar carga inicial informativa, revalidación suave, vacío y error recuperable; una mutación fallida conserva el modal y sus valores. Textos y toasts ES/EN.

Si se exige que cada página contenga grupos completos, cambia la semántica de paginado y requerirá otro contrato con hijos acotados; no es parte de este ajuste mínimo.

## Implementación local y SQL aislada de FX-02 — 2026-10-25
