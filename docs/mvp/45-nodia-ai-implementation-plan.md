Cambio de alcance confirmado el2026-10-14 en[48](48-nodia-ai-mode-routing-policy.md): Web sólo conversación; Agentic con MCP. ## Cómo Server cargará ese contexto

AI-06 implementa autoría validada y compilación de build conforme52. AI-12 incorpora loader/startup, filtro por actor, armado canónico, selección de detalle por IDs y herramientas técnicas MCP en[58](58-nodia-ai-ai12-context-execution.md), con pruebas aisladas y aceptación Gemini real pendiente. Corpus actual43 draft/unregistered, bundle vacío: el mecanismo implementado no publica fichas ni herramientas de negocio.

1. **Autoría (AI-06):** Markdown con frontmatter JSON único de identidad/revisión/estados/fuentes/verificación/aprobación. El registro de código vincula capacidades/módulos con secciones explícitas; aprobación humana y elegibilidad se comprueban sin autoaprobar. Paths listados, sin descubrir carpetas para habilitar funciones.
2. **Build (AI-06):** knowledge:check antes de Nest y knowledge:build después de deleteOutDir emiten `dist/nodia-ai/knowledge/manifest.json` y sólo fragmentos elegibles content-addressed. Hashes de registro/schema/documentos/contratos/fragmentos y catálogo fijan el release; corpus actual37 borradores,0 assets de contenido. ADR/runbooks/AGENTS son trazabilidad, no texto concatenado al prompt. Comparador de revisiones requiere baseline anterior de confianza cuando exista; CI/deploy AI-36/38 pendiente.
3. **Arranque:** `LoadNodiaAiKnowledgeUseCase`, en `nodia-ai-context/`, lee los assets compilados y un pin de despliegue separado; verifica schema/hashes/bindings. No depende de que `docs/` exista en el VPS ni descarga el repo. Archivo faltante/incompatible bloquea el arranque, sin contexto inventado. API/worker admiten/reclaman únicamente catálogo/release compatibles; rolling deploy y publicación productiva siguen pendientes.
4. **Admisión del turno:** fijar selección exacta y release. Resolver autoridad actual antes de mostrar índice de productos/capacidades. Entregar sólo descripciones breves autorizadas y reglas comunes; no enviar los27 documentos completos a cada mensaje. Un resumen de producto con distintos destinos debe contener únicamente conceptos seguros; su detalle administrativo no se filtra por tener un solo submódulo.
5. **Selección de detalle:** el contexto inicial contiene resúmenes de producto e índice autorizado, sin leer todas las funcionalidades. Agentic solicita IDs exactos mediante `nodia_knowledge_index`/`nodia_knowledge_get`, con grant/fence vigentes, el mismo release y límites previos de lectura/resultado; las fuentes añadidas registran revisión y hash. Ante ambigüedad se pregunta; no se deduce el ámbito por expresiones regulares ni se inspecciona la BD para entender un producto. Web no recibe herramientas: sólo puede solicitar una delegación tipada cuando existe consentimiento explícito hacia el destino Agentic exacto.
6. **Contexto y datos:** combinar instrucciones comunes controladas, conceptos relevantes, historial/snapshot válido, preferencias aceptadas y refs de propuestas/recibos. Los datos de BD se consultan con herramientas permitidas. Persistir en runs.context_manifest referencias de las fuentes seleccionadas en checkpoints, con versión/hash y ámbitos; no almacenar otra copia de todos los documentos/prompts. Release fijo y manifiesto de fuentes acumulado son conceptos distintos.
7. **Caché y presupuesto:** cachear documentos públicos parseados por release/hash; filtrar/reautorizar por sesión/ámbito en cada despacho. No compartir historial, datos de negocio o memorias en una caché global. Medir presupuesto real por adaptador/modelo; cargar detalles bajo demanda y compactar conversación sin perder acciones/recibos. Si el modo no ofrece medición/capacidad suficiente, informar limitación y evitar truncado silencioso.
8. **Evolución:** desplegar ficha + contrato + herramienta + pruebas juntos. Un producto nuevo no necesita cambios al esquema conversacional. Siguiente turno de un chat vigente descubre el release actual; ejecución admitida conserva el suyo. En rolling deploy, worker sólo reclama versiones soportadas; si falta una versión, detener/conciliar según fase sin reinterpretar comandos. Invalidar propuestas incompatibles; conservar identidad y receipts. Retirar paquetes antiguos cuando no haya trabajo que los requiera bajo política de operación.

Para estas cargas se propone un lector simple por registro/IDs, con índice acotado de conceptos. No se requiere embeddings, entrenamiento, acceso libre a endpoints o inspección de BD para entender funciones. Registrar las fuentes efectivamente enviadas permite diagnosticar respuestas sin guardar secretos ni prompts completos. [Recursos MCP oficiales](https://modelcontextprotocol.io/specification/2025-11-25/server/resources) describen un transporte de contexto, no la autorización ni la viabilidad de los adaptadores de Nodia.
