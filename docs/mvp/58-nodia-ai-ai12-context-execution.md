## KnowledgeRegistry

El build compila las fichas mediante AI-06 y empaqueta manifiesto/fragments, schema estricto y un pin de despliegue separado del bundle. El loader no explora `docs/`, endpoints o tablas para deducir productos. Valida schema, claves JSON duplicadas, release/hash, catálogo, referencias y registros ejecutables compatibles. El pin es parte confiable del artefacto desplegado: un hash no sustituye la aprobación humana ni firma el contenido. Cambiar de release exige construir/desplegar un nuevo artefacto.

Sólo se leen bytes de fragmentos autorizados para todos sus módulos y ligados a capacidades registradas. Antes de leerlos se suma su tamaño declarado y se rechaza el conjunto que excede el presupuesto de contexto. Rutas fuera del bundle, symlinks, tamaños/hashes inconsistentes y capacidades documentales sin implementación fallan cerrados. La caché contiene únicamente bytes del release, nunca historial o permisos, y queda acotada por ese mismo presupuesto. El registro ejecutable de capacidades de negocio sigue vacío hasta AI-14; las fichas draft/unregistered quedan excluidas. Un bundle vacío es válido y se comunica al modelo: no significa que conozca todos los productos.

La carga inicial incluye sólo fragmentos `product_summary` y un índice autorizado de metadatos; no lee el texto completo de las funcionalidades por anticipado. El índice conserva los propósitos existentes `product_summary`, `feature_explanation` y `report_semantics`, IDs exactos, revisión documental, secciones, hash y bytes. El detalle se solicita por IDs explícitos del mismo release, sin clasificación por expresiones regulares, embeddings o acceso libre a archivos.

## ContextBuilder y admisión

El preparador obtiene observación real del adaptador fuera de la transacción; una referencia privada inmutable la vincula a actor, sesión, chat, revisión y selección. Dentro del commit revalida configuración y frescura y congela release, scopes y generación de sesión. Una API guardada, un catálogo o una sesión autenticada no acreditan inferencia real. API queda deshabilitada para esta vía de v1.

El worker vuelve a autorizar. El contexto de un run puede reducirse por revocación, nunca ampliarse porque se asignen módulos nuevos después de admitirlo. La historia se corta en la secuencia admitida y se arma con roles/campos explícitos, sin depender de una conversación opaca del proveedor. Los mensajes con origen desconocido o no autorizado se sustituyen por una marca restringida antes de cargar sus partes. El manifiesto por run registra release, fragmentos, secuencia, hash y tamaño del contexto; no duplica el prompt en otro almacenamiento.

Hay límites explícitos de bytes y elementos antes de cargar el historial. Un exceso devuelve `context_limit` sin truncar decisiones o inventar un resumen. Compactación, adjuntos y preferencias quedan para sus etapas; las modalidades no verificadas no se envían silenciosamente como texto.

## Pipeline y modos

Etapa `context` construye/verifica y guarda procedencia; etapa `inference` observa la misma selección, reserva el perfil y arma el dispatch durable antes de llamar al adaptador. Respuesta válida, mensaje asistente, cierre del run y liberación del slot se confirman atómicamente; la respuesta no renueva los 90 días. Cambios de generación/configuración, proveedor caído y pérdida del lease bloquean el dispatch/commit conforme a la fase. Una respuesta tipada debe incluir la prueba privada de cierre nativo, ligada a intento/perfil/sesión/operación; el commit crea una tarea independiente para acusar recibo fuera de SQL y limpiar la prueba mínima.

Web conserva el contrato cerrado `answer`/`delegation_request`, sin herramientas. Agentic puede recibir únicamente `nodia_knowledge_index` y `nodia_knowledge_get` cuando el adaptador acredita MCP para la selección/generaciones exactas. Estas dos lecturas técnicas no registran herramientas de negocio ni habilitan SQL, endpoints arbitrarios o escrituras. `index` exige argumentos vacíos; `get` admite de 1 a 8 IDs únicos de hasta 256 bytes UTF-8. El resultado se limita a 64 KiB y los argumentos al máximo de50; se valida autoridad, grant, lease y fence antes de cada lectura. Cada callback se deduplica por run/callId y contrato/argumentos; los detalles incorporados anexan referencias con revisión y hash al manifiesto, sin duplicar el prompt.

El transporte privado informa el total monótono de mensajes RPC reales por intento; Server reserva sólo su incremento en el presupuesto durable común del run. El máximo de 128 RPC y 12 llamadas a herramientas no se reinicia al cambiar de etapa. Los límites son propios de Nodia, no cuotas del proveedor. Una pérdida de autoridad o una respuesta incierta no habilitan replay o cambio de modo.

Cada solicitud de herramienta consume presupuesto incluso si sus argumentos se rechazan o recupera un resultado previo. El callback visible reserva y confirma su cupo antes de la validación/lectura que puede fallar; el efecto y su recibo siguen idempotentes. El puente Native cuenta también solicitudes inválidas o replays resueltos sin callback a Server; publica su acumulado no reenviado y Server reserva sólo el delta, sin contar dos veces las llamadas visibles. Retrocesos, totales inválidos y exceso fallan cerrados; no se pierden los consumos anteriores por rollback de una lectura posterior.

`PATCH /api/v1/nodia-ai/conversations/:id/routing` materializa el consentimiento humano revisionado. Habilitar exige chat propio e inactivo, selección base Web y destino Agentic disponible con MCP verificado, de la misma conexión y con el modelo/esfuerzo configurados para ese modo. No copia el modelo Web ni toma el primero descubierto. La observación ocurre fuera de SQL y se revalida con configuración/sesión dentro del commit. Deshabilitar funciona incluso durante un run y sin contactar al proveedor; una revisión anterior no autoriza un nuevo dispatch delegado.

Con el consentimiento encendido, una solicitud tipada de Web cierra y libera primero su intento y encola `delegated_inference` dentro del mismo run. La fase Agentic revalida consentimiento y disponibilidad, adquiere su perfil y consume los presupuestos compartidos de dispatch/delegación. La selección base permanece Web para el siguiente turno. Sin consentimiento, la petición de delegación se presenta como explicación conversacional. No hay loops, delegación por error, destino API ni confirmación de escrituras implícita. El drawer/switch visual pertenece a AI-13; las operaciones de negocio siguen AI-14 y familias posteriores.
