## Ejecución

`nodia-server/src/nodia-ai-worker.ts` compone un proceso Nest sin listener HTTP. `npm run worker:nodia-ai` consume un build ya preparado y una BD migrada; no migra al arrancar. La API puede importar módulos/casos de uso sin arrancar loops. Dos consumidores foreground y un coordinador de mantenimiento usan los límites de la política versionada; varios procesos comparten capacidad SQL.

Cada claim tiene una sola etapa, intento, worker UUID, lease y fence. Claims usan transacciones cortas, selección `SKIP LOCKED` y un gate de admisión compartido que ordena los límites globales/por usuario. Orden común: autoridad, gate de cola, chat, job. El gate serializa sólo admisión/checkpoints breves, nunca la inferencia. Se vuelve a comprobar sesión, grant, época de retención, política y catálogo soportado. La expiración usa reloj actual después de los locks.

Contexto avanza a inferencia mediante un checkpoint atómico; el resultado y la transición se guardan juntos. Justo antes de enviar al proveedor se reserva presupuesto durable y se marca `dispatch_armed`. Los heartbeats renuevan job y slot físico vigentes; un worker tardío no puede escribir ni liberar recursos de un fence posterior. No hay SQL abierto durante HTTP/CLI, generación o espera del usuario.

La espera en cola y el deadline total son independientes; cambiar de etapa no reinicia ninguno. Reintentos se limitan a fallos conocidos antes del dispatch, con presupuesto y demora de la política. Después de un dispatch armado, caída/timeout/pérdida de respuesta produce `unknown`, no un reenvío automático. El drain deja de admitir, espera un tiempo acotado y aborta lo restante sin declararlo terminado.

## Perfil físico compartido

El adaptador privado identifica el perfil real resuelto mediante hash; la conexión o el nombre de modelo no son la identidad del recurso. Los slots SQL reservan fence/operación y no se liberan por TTL. Sólo una respuesta terminal verificada permite liberar el slot en el mismo commit que sella el resultado.

El servicio Gemini añade una puerta por perfil para chat, OCR, login, logout, refresh y descubrimiento. Login conserva la reserva durante su tarea. Un marcador mínimo persistente impide reutilizar un perfil tras un resultado incierto o un crash; no contiene prompts. SQL y servicio nativo tienen responsabilidades distintas: coordinar workers y proteger también consumidores ajenos al chat. Ninguno sustituye al otro.

## Verificación y pendientes

### Conciliación operativa sin replay

`ReconcileNodiaAiRuntimeUseCase` exige una sesión actual de super_admin con acceso a NodiaAI; no restaura el grant revocado del turno. La petición nativa se liga al intento original, perfil físico, generación de sesión y referencia de operación. Sólo acepta un recibo terminal privado, con identidad de prueba y cierre de procesos comprobados por el supervisor. Una ausencia de PID, un timeout, el TTL o una casilla enviada por el operador no constituyen esa prueba. Los unknown históricos que no tengan identidad suficiente continúan bloqueados.

Una prueba `completed` puede cerrar el turno local como fallido con `response_unavailable` cuando se perdió la respuesta: no inventa texto ni vuelve a pedir la generación. `abandoned_unknown` conserva esa incertidumbre mediante `outcome_unknown`; no afirma ausencia de efectos remotos. El mismo commit revoca grants, libera la actividad, invalida el fence y libera exclusivamente el slot coincidente. La recuperación de operaciones de negocio futuras conserva sus recibos y su contrato de AI-20; este puerto sólo concilia el runtime conversacional.

El acuse de eliminación del recibo nativo ocurre después del commit SQL y es idempotente. Si falla o se pierde la respuesta, queda un job `reconcile_ack` con identidad mínima; el coordinador lo procesa cada heartbeat y aplica cinco intentos con las esperas de la política. Agotarlos conserva un pendiente visible para el operador. Una intervención explícita puede intentar sólo ese acuse otra vez, sin ampliar la generación. Tras verificar el acuse se borran el job y sus intentos; no comienza otra retención de auditoría. La purga del chat conserva exclusivamente los identificadores necesarios para este cierre, sin mensajes, modelos, configuración completa o prompts.

El camino normal de éxito también incluye una prueba terminal privada y crea su job separado de acuse en el mismo commit que guarda el resultado. Ese pendiente no depende del chat o del run y no expone la prueba en sus proyecciones públicas. Así la purga no elimina la única referencia necesaria para limpiar el recibo nativo. Una respuesta exitosa sin prueba verificable no libera el slot. En cambio, una reserva local cuyo intento sigue `claimed` puede liberarse al fallar o vencer: la barrera durable demuestra que todavía no se permitió llamar al proveedor.

Operación interna, sin nueva ruta HTTP: `node scripts/reconcile-nodia-ai-runtime.mjs --list` lista hasta la página configurada de pendientes técnicos; reemplazar `--list` por su UUID inicia la conciliación o reintenta el acuse pendiente. El proceso recibe `NODIA_AI_OPERATOR_ACCESS_TOKEN` por el entorno y valida la firma, audiencia, emisor y vigencia del access token, además de releer sesión/rol/módulo dentro de cada frontera transaccional. Nunca introducir el token en argumentos, logs o documentación. El comando no migra ni arranca workers y no contiene ninguna llamada de generación.

Casos de uso, PostgreSQL16 real desechable y procesos worker sintéticos comprueban fences, capacidad, exclusión, pérdida de lease, rollback, recuperación y ausencia de replay. La [integración AI-11](../evidence/nodia-ai-ai11-postgres-integration.json) incluye dos procesos Node competidores y la terminación forzada de un worker después de armar el envío; los proveedores de ese ensayo son sintéticos y no demuestra cancelación de una inferencia externa real. Python verifica exclusión/cancelación con servicios simulados. [Evidencia conjunta](../evidence/nodia-ai-ai10-ai12-validation.json).

La [matriz real de concurrencia anterior](../evidence/nodia-ai-ai11-ai12-live-concurrency.json) pasó13 comprobaciones de MCP, exclusión chat/OCR/login/discovery e independencia de perfiles. Dos diagnósticos inciertos se conciliaron sin replay; uno completó CLI/MCP pero fue rechazado por una denegación previa del hook. El catálogo explícito posterior permitió completar la matriz sin relajar el guard.

La [verificación final](../evidence/nodia-ai-ai11-ai12-live-validation.json) cerró los pendientes tras retomar la VM: [9 checks del proceso worker independiente](../evidence/nodia-ai-ai11-ai12-live-agentic-worker.json), [10 de delegación](../evidence/nodia-ai-ai11-ai12-live-routing.json) y [13 de cancelación/conciliación](../evidence/nodia-ai-ai11-ai12-live-unknown.json). El entrypoint real `dist/nodia-ai-worker.js` consumió el turno Agentic desde una BD desechable, llamó MCP técnico, selló respuesta y slot y terminó por SIGTERM con acuse limpio. La cancelación ocurrió en un callback real, después del checkpoint SQL y antes de entregar su resultado al CLI: run/job/slot quedaron `unknown`, sin respuesta fabricada ni replay; la prueba nativa `abandoned_unknown` permitió conciliar como super_admin, acusar recibo y liberar capacidad. El perfil pudo observarse disponible después.

Se verificaron cero marcadores inciertos, recibos nativos y procesos/containers de prueba al finalizar. Los servicios habituales quedan levantados; el Server nuevo se ensayó en staging, sin migraciones/escrituras de negocio en la BD configurada. El harness conserva SQL y recovery mínimo también si falla el checkpoint y no llega a publicarse `unknown`.
