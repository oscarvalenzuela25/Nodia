# AI-38: observación de reservas del perfil y adopción propuesta

Revisión técnica solicitada para identificar al propietario real de `runtime_busy` durante una recarga. Este corte es exclusivamente de lectura; no adopta una imagen, reinicia servicios, llama endpoints ni genera inferencia.

## Hechos comprobados

El [inventario nuevo](nodia-ai-ai38-profile-reservation-inventory-r01.json) observa el contenedor `802d6d…`, imagen `b8efad…` y comienzo `2026-10-20T19:14:35.412657745Z`, sin cambio de época durante la lectura. Las 47 fuentes Python de primer nivel `/app/*.py` se hashean sin importar módulos de aplicación ni abrir perfiles, sesiones o login. No equivalen al inventario recursivo de 85 fuentes de cortes anteriores. `profile_admission.py` conserva SHA-256 `46426d6920fbf249c6769a5d4fc1f55d1a114b35ae8e348020fe77be0c9a8bdb`, igual a la fuente local inspeccionada antes de instrumentar.

API y worker conservan el Server `nodia-server-ai38-owner-r01`; el journal externo continúa abierto desde `2026-10-20T23:52:27.154Z`, sin entradas no confirmadas y con seis backups registrados. El observador encuentra cero jobs/intentos/slots SQL y cero artefactos nativos pendientes. Esto describe ese instante; no demuestra qué operación ocupaba el perfil durante el 409 histórico.

El [intervalo HTTP R03](nodia-ai-ai38-probe-http-metadata-r03.json) observa `POST /nodia-ai/agentic/observe` →409 a `18:00:08.672315Z`, y una observación posterior →200 a `18:01:32.640972Z`. La ruta agregada `/engines/status` utiliza internamente `agentic_status()`. Las marcas de final de HTTP no muestran su instante de adquisición ni la identidad del propietario de la reserva; no acreditan que esa ruta haya causado el 409.

La implementación actual guarda un conjunto `_held` por identidad física y cuarentena separada. No conserva el tipo de operación propietaria, su instante de adquisición ni correlación de adquisición/rechazo/liberación. No hay contrato de diagnóstico que permita obtener hoy ese propietario sin instrumentar el proceso. No se intenta reconstruirlo leyendo memoria, archivos de autenticación o perfiles.

## Instrumentación recomendada, aún propuesta en este documento

Mantener la exclusión por perfil físico, un proceso/worker y las reglas de cuarentena. En cada reserva, conservar únicamente un registro técnico en memoria: ID aleatorio interno de reserva, operación de un vocabulario cerrado, correlación generada por el servidor y reloj monotónico de adquisición. Una reserva retenida por una tarea de login/MCP conserva ese mismo propietario hasta la finalización real. Los alias de motor que comparten un perfil deben señalar al mismo propietario físico.

Emitir eventos estructurados cerrados de adquisición, rechazo por ocupación, liberación y cuarentena. El rechazo debe enlazar el solicitante con el propietario ya almacenado y su antigüedad monotónica; no inventar un propietario si procede de un marcador histórico de cuarentena. La liberación verifica que el ID siga perteneciendo a esa reserva. No registrar rutas arbitrarias, queries, mensajes, documentos, cuerpos, tokens, cabeceras de autenticación, valores del perfil ni identificadores del usuario. No añadir un historial durable propio o un endpoint público: basta con el logger operativo existente y una proyección acotada de esos eventos para la aceptación.

`PrivateRequestGuard` ya genera `request_id = uuid4().hex` dentro del servidor. Se puede propagar mediante un contexto de tarea, copiándolo en la reserva al adquirirla; nunca copiar un encabezado libre del cliente como etiqueta de operación. Las llamadas de arranque o tareas sin HTTP requieren etiquetas internas explícitas. No usar `inspect.stack()`, frames de tareas o argv para inferir el propietario.

El campo de operación debe cubrir health/discovery/observación/chat/OCR/login/refresh/logout y MCP durable con etiquetas específicas. El cierre del HTTP no libera una reserva transferida a una tarea que sigue ejecutándose. `runtime_busy` puede provenir de trabajo legítimo, de sondeo no generativo o de cuarentena; el diagnóstico debe distinguirlos sin desbloquear o reenviar automáticamente una inferencia incierta.

## Adopción precisa propuesta

1. Congelar la imagen base exacta `sha256:b8efad6217a4f04cb135db027fd899c1826b39c3a16154cca79f1b4f0deb977e`, sus fuentes y el conjunto explícito de archivos modificados. Crear una imagen derivada desde ese ID con solo esas fuentes productivas; no reconstruir dependencias/CLI contra Internet ni incorporar `.env`, `browser_profile`, `session_state`, pruebas con credenciales o claves. Ejecutar las pruebas aisladas del runner del repositorio y comprobar inventario/diff completos antes de adoptar.
2. Guardar en un directorio privado propio los descriptores actuales efectivos de Gemini/Compose y sus hashes; no imprimir su entorno. Capturar epoch, imagen, hashes de entorno/montajes/recursos, paquete Server/Client y estado de backups/journal. Preparar override nuevo de imagen con `pull_policy: never`, preservando usuario, seis montajes, loopback, límites y un worker. No reutilizar la antigua reversión que apuntaba al Server de 932 outputs sin journal.
3. Cerrar tráfico de prueba y admisión API, permitiendo al worker terminar. Comprobar quietud SQL y nativa con los helpers fijados; si hay resultado incierto o trabajo activo, detener la transición y conciliar. Solo después de comprobar cero pendientes, detener el worker. Pausar timers de backup/rotación únicamente durante la transición y conservar su estado inicial. No matar una operación nativa para ganar quietud.
4. Recrear únicamente Gemini desde la imagen congelada candidata. La nueva imagen no está montada como código y Python ejecuta `workers=1, reload=False`: **la instrumentación efectiva obliga a una época nueva**. No parchear módulos dentro de un proceso vivo ni afirmar que se preservó su atestación anterior. Preservar el journal y todos sus marcadores; no bootstrap, close, restore ni eliminación de `.unknown`/proofs.
5. Verificar imagen, inventario, entorno/montajes/recursos por hashes y mismo paquete Server journalado. Reiniciar API/worker desde sus descriptores actuales y restaurar timers. Liveness200, autenticación y descubrimiento no acreditan inferencia ni MCP: mantener separada la evidencia histórica de la época nueva y verificar explícitamente la selección persistida antes del chat.
6. Reproducir una recarga autenticada y proyectar solo eventos cerrados de reservas y endpoints. La aceptación exige que cada rechazo ocupado encuentre un propietario adquirido previamente, sin liberación anterior y con operación/correlación comprobables; después de su finalización real debe observarse liberación y recuperación. Capturar éxito, excepción, cancelación y cuarentena en tests aislados, y una reproducción real sin efectos comerciales ni reenvío de resultados inciertos.

## Reversión y límites

Revertir exclusivamente el override propio de Gemini a la imagen base `b8efad…`, manteniendo Server `owner-r01` y el journal abierto. Aplicar el mismo cierre de admisión, drenaje/quietud y validación de estado antes de recrear. Restaurar descriptor byte a byte, entorno/montajes/recursos y timers previos; no restaurar BD, sesiones o pruebas antiguas. La reversión también crea otra época y exige comprobar de nuevo disponibilidad; no recupera la identidad de contenedor ni las pruebas runtime anteriores.

Ante una transición incompleta, conservar API cerrada y el worker ocupado drenando. No apagar forzosamente, borrar marcadores, cambiar de proveedor/modelo, repetir una inferencia ni arrancar un escritor sin journal. La instrumentación puede identificar el propietario de un rechazo posterior; no demuestra retrospectivamente la causa del 409 de las 18:00:08. Aún no se ejecutó esta adopción, reversión ni una reproducción con instrumentación.
